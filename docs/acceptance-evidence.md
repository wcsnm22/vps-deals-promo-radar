## 6. 第 10 步这一轮改了什么（2026-10-01）

这一节只记这一轮实际动过的东西和核验方式。

### 6.1 修掉一个会断更的 bug

| 项 | 证据 |
|---|---|
| 现象 | 2026-10-01 09:00 那次日更 `content_check_exit: 1`、`deploy_exit: 1`：`unitprice-2026-10-01-1.html` 被判"lede 里没有任何数字"，于是当天没发布、也没推 git。见 `data/daily-log.jsonl` 的最后一行 |
| 根因一 | `guides.py` 按"第几个 unitprice 页"轮换主题厂商，轮到了 netcup——而 netcup 当时抽不到内存，页面上算不出单价，第一屏自然没有数字 |
| 根因二 | `scraper.py` 的规格正则要求"数字和 RAM 在同一行"，netcup 的卡片是 `4 GB` 和 `RAM` 分成两个元素，所以内存一直读不到（页面因此写着"netcup publishes no RAM figure"，而这句和它页面上的实际内容不符） |
| 修法 | 1) `scraper.py` 增加 HTML 层"值 + 标签"配对读取，只认页面自己印出来的规格标签；2) `guides.py` 的 unitprice 只在"能算出单价的厂商"里轮换，且换不出带数字的答案就换下一个缺口 |
| 回归 | 改后重抽：OVHcloud / BuyVM / IONOS / Hostwinds / Hetzner 的抽取结果与改前**逐字段一致**，只有 netcup 从 0 条带内存变成 10 条全带内存 |
| 结果 | 同日重跑全链路：`scraper 0 / guides 0 / build 0 / content_check 0 / git 0 / deploy 0 / verify 0`，当天页面已上线，`14/14 篇通过` |

### 6.3 一次"看起来成功了但线上没变"的核对

| 项 | 证据 |
|---|---|
| 现象 | 指南页的新内容（问答、互链、可见日期、单价图）都上线了，但**首页还是旧版**：既没有第一屏答案框，也没有单价图 |
| 为什么没被发现 | `verify_deploy.py` 原来只核对 `sitemap.xml` 与本次构建是否一致。sitemap 一致只说明"构建过"，不说明"每一页也跟着上线了"；首页旧版和构建版的 sitemap 片段是一样的，比不出来 |
| 修法 | `verify_deploy.py` 增加一步：内容一致后，再抓线上首页，确认它带着本次构建的答案框（`class="answer"`）；不带着就判失败。这一条现在会跟着每日任务自动跑 |
| 核对结果 | 修好后重跑：`线上首页带着 gtag 与衡量 ID` + `首页 线上带着本次构建的内容（/）`，线上首页确实带上了答案框和单价图 |

### 6.4 GSC 报的结构化数据问题（2026-10-02）

操作者从 Search Console 发来一个富媒体结果的下钻地址，`item_key` 解出来是
`offers` / `review` / `aggregateRating`——指向的正是商品类结构化数据。逐页查了线上的 JSON-LD：

| 发现问题 | 在哪 | 为什么算错 |
|---|---|---|
| `Product` 没有 `offers` | `/provider/digitalocean`、`/provider/hetzner` | Google 对 Product 的必填字段就是 `name` + `offers`。这两家我们读不到价格，于是发了一个没有 offers 的 Product——这是硬错误，不是警告 |
| `AggregateOffer` 没有 `priceValidUntil` | 5 个有价格的厂商页 | 这个字段属于**商家信息**（merchant listing）的校验口径，而商家信息还要求退货政策、运费政策。我们是比价站，不卖东西 |
| 裸 `Offer`（没有外层 Product） | 25 个 `/deal/*` 页 | Google 不认这种形状；它同样把页面拉进商家信息口径，缺 `priceValidUntil` 就报 |

| 怎么改的 | 证据 |
|---|---|
| 不再发 Product / Offer / AggregateOffer | `build.py`：厂商页改成 `WebPage` + `ItemList`（每条带 `position`、`url`、`description` 里写厂商公布的价格）；`/deal/*` 页改成 `WebPage` |
| 为什么不补 `priceValidUntil` | 数据集里 25 条优惠**没有一条**有 `valid_until`（厂商页上没写有效期）。为了消警告去编一个有效期，违反 `.ilang/site.ilang` 的 `BOUNDARY{never:编优惠 编价格 编有效期}`。所以改口径，不改数据 |
| 构建时自查 | `build.py` 新增 `audit_structured_data()`：扫 `site/` 下每个页面的 JSON-LD，发现"没有 offers 的 Product""没有 price 的 Offer""没有 lowPrice 的 AggregateOffer"或非法 JSON 就**直接让构建失败**。自测：基线 0 问题；塞进这两种坏标记后各报一条；删掉后归零 |
| 线上核对 | 修复已部署。重抓全部 12 个抽样页面：`Product` / `Offer` / `AggregateOffer` 一个都不剩，`/provider/*` 是 `WebPage` + `ItemList` + `BreadcrumbList`，`/deal/*` 是 `WebPage` + `BreadcrumbList`，首页与 `/compare` 的 ItemList 25 条都带 `position` 和 `url` |

Search Console 里那条旧的富媒体结果条目在重新抓取后会消失（因为页面上不再有商品类标记）。
这个修复只解决"标记和事实不符"的问题，不碰排名，也不承诺任何富媒体展示。

### 6.5 这一轮仍然没拿到的

## 7. 对标复盘与选题队列（STEP:10 `rival_growth_teardown`，2026-10-03）

命令要三件交付物：① 页面矩阵分类表 ② 带流量的词清单 ③ 排好序的选题队列。三件都在
`docs/rival-growth-teardown.md` 和 `data/rival-*.json` 里，能指到原始记录。

| 交付物 | 在哪 | 数字来源 |
|---|---|---|
| ① 页面矩阵分类表 | `docs/rival-growth-teardown.md` 第 3 节 + `data/rival-matrix.json` + `data/rival-depth.json` | 对手自己公开的 sitemap 与页面结构（标题层级、正文词数、表格/列表数），只存指标不存正文 |
| ② 带流量的词清单 | 报告第 2 节；有 GSC 导出时用真数字，没有时照实写"没拿到" | `data/rival-keyword-signals.json`（公开搜索补全的真人查询原话）或 `data/gsc-queries.csv`（操作者从后台导出） |
| ③ 选题队列 | 报告第 8 节 + `data/rival-topic-queue.json` | 三信号排序：我们写没写过 → 补全里排第几（或有流量数据时用后台展示次数）→ 几家对手在做 |

| 这一轮的规矩 | 落点 |
|---|---|
| 不照抄对手原文 | `rival_teardown.py::overlap_check()` 把双方页面切 5-gram 算重合率，对手正文只在内存参与计算、**一字原文都不落盘**。实测：对手 8 页 × 我们 55 个内容页，**内容页最高重合 0.9524%**（6 个 5-gram，出现在 `/about.html`），全站最高 3.7037% 来自只有导航页脚的 `/404.html`。可复跑：`python rival_teardown.py overlap` |
| 不把第三方估算当准数 | 队列排序里没有任何 Ahrefs/Semrush/AITDK 的数字；代码里写成 `::BOUNDARY{never:把 AITDK / sitedata 这类估算当判据|scope:permanent}` |
| 有流量的词只认自家后台 | `rival_queue.py::load_gsc_queries()` 读 `data/gsc-queries.csv`（GSC → 效果 → 查询 → 导出 CSV），拿到就把排序第一判据换成真实展示次数；拿不到就照实说没有 |
| 对手拒绝就别碰 | `www.pcmag.com` 的 robots.txt 返回 403 → 整站跳过，一个页面都没抓；`vpsfilter.com` robots.txt 404（无文件）且 sitemap 只有 2 条地址、首页是 JS 空壳（我们不执行站外脚本），所以它只有"页面数"这一个结论 |

仓库体积也顺手治了：12,572 条 URL 的原始清单不再塞进 `data/rival-matrix.json`（原来 1.99 MB），
改存 `data/rival-urls.json.gz`（261 KB），矩阵文件降到 30.8 KB，队列脚本只读这份缓存、不重复抓别人的 sitemap。

### 7.1 从这次对标里得到的两条硬结论
- **对手的门面是根级常青榜单页**：lowendbox 12,572 条地址里 `/blog/` 的按时间优惠单页占 6314 条，
  真正撑门面的是少数根级榜单页（`/best-cheap-vps-hosting-updated-2020/` 这类）。我们 25 个 `/deal/*` 页
  相当于他们的优惠单页，缺的是根级榜单页——这是选题队列之外的结构性缺口。
- **三个对手都没做多语言**：lowendbox 那 6042 个"标签归档页"是 `/tag/io/`、`/tag/me/` 这类域名后缀标签，
  不是语言版本。所以多语言这一条不列为任务（没有可抄的动作）。
