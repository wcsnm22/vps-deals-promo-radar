## 6. 第 10 步这一轮改了什么（2026-10-01）

这一节只记这一轮实际动过的东西和核验方式。

### 6.1 修掉一个会断更的 bug

| 项 | 证据 |
|---|---|
| 现象 | 2026-10-01 09:00 那次日更 `content_check_exit: 1`、`deploy_exit: 1`：`unitprice-2026-10-01-1.html` 被判"lede 里没有任何数字"，于是当天没发布、也没推 git。见 `data/daily-log.jsonl` 的最后一行 |
| 根因一 | `guides.py` 按"第几个 unitprice 页"轮换主题厂商，轮到了 netcup——而 netcup 当时抽不到内存，页面上算不出单价，第一屏自然没有数字 |
| 根因二 | `scraper.py` 的规格正则要求"数字和 RAM 在同一行"，netcup 的卡片是 `4 GB` 和 `RAM` 分成两个元素，所以内存一直读不到（页面因此写着"netcup publishes no RAM figure"，而这句和它页面上的实际内容不符） |
| 修法 | 1) `scraper.py` 增加 HTML 层"值 + 标签"配对读取，只认页面自己印出来的规格标签；2) `guides.py` 的 unitprice 只在"能算出单价的厂商"里轮换，且换不出带数字的答案就换下一个缺口 |
| 回归 | 改后重抽：OVHcloud / BuyVM / IONOS / Hostwinds / Hetzner 的抽取结果与改前**逐字段一致**，只有 netcup 从 0 条带内存变成 10 条全带内存 |
| 结果 | 同日重跑全链路：`scraper 0 / guides 0 / build 0 / content_check 0 / git 0 / deploy 0 / verify 0`，当天页面已上线，`14/14 篇通过` |

### 6.3 一次"看起来成功了但线上没变"的核对

| 项 | 证据 |
|---|---|
| 现象 | 指南页的新内容（问答、互链、可见日期、单价图）都上线了，但**首页还是旧版**：既没有第一屏答案框，也没有单价图 |

### 6.4 GSC 报的结构化数据问题（2026-10-02）

操作者从 Search Console 发来一个富媒体结果的下钻地址，`item_key` 解出来是
`offers` / `review` / `aggregateRating`——指向的正是商品类结构化数据。逐页查了线上的 JSON-LD：

| 发现问题 | 在哪 | 为什么算错 |
|---|---|---|
| `Product` 没有 `offers` | `/provider/digitalocean`、`/provider/hetzner` | Google 对 Product 的必填字段就是 `name` + `offers`。这两家我们读不到价格，于是发了一个没有 offers 的 Product——这是硬错误，不是警告 |
| `AggregateOffer` 没有 `priceValidUntil` | 5 个有价格的厂商页 | 这个字段属于**商家信息**（merchant listing）的校验口径，而商家信息还要求退货政策、运费政策。我们是比价站，不卖东西 |
| 裸 `Offer`（没有外层 Product） | 25 个 `/deal/*` 页 | Google 不认这种形状；它同样把页面拉进商家信息口径，缺 `priceValidUntil` 就报 |

| 怎么改的 | 证据 |
|---|---|
| 不再发 Product / Offer / AggregateOffer | `build.py`：厂商页改成 `WebPage` + `ItemList`（每条带 `position`、`url`、`description` 里写厂商公布的价格）；`/deal/*` 页改成 `WebPage` |
| 为什么不补 `priceValidUntil` | 数据集里 25 条优惠**没有一条**有 `valid_until`（厂商页上没写有效期）。为了消警告去编一个有效期，违反 `.ilang/site.ilang` 的 `BOUNDARY{never:编优惠 编价格 编有效期}`。所以改口径，不改数据 |
| 构建时自查 | `build.py` 新增 `audit_structured_data()`：扫 `site/` 下每个页面的 JSON-LD，发现"没有 offers 的 Product""没有 price 的 Offer""没有 lowPrice 的 AggregateOffer"或非法 JSON 就**直接让构建失败**。自测：基线 0 问题；塞进这两种坏标记后各报一条；删掉后归零 |
| 线上核对 | 修复已部署。重抓全部 12 个抽样页面：`Product` / `Offer` / `AggregateOffer` 一个都不剩，`/provider/*` 是 `WebPage` + `ItemList` + `BreadcrumbList`，`/deal/*` 是 `WebPage` + `BreadcrumbList`，首页与 `/compare` 的 ItemList 25 条都带 `position` 和 `url` |

Search Console 里那条旧的富媒体结果条目在重新抓取后会消失（因为页面上不再有商品类标记）。
这个修复只解决"标记和事实不符"的问题，不碰排名，也不承诺任何富媒体展示。

`docs/rival-growth-teardown.md` 和 `data/rival-*.json` 里，能指到原始记录。

| 交付物 | 在哪 | 数字来源 |
|---|---|---|
| ① 页面矩阵分类表 | `docs/rival-growth-teardown.md` 第 3 节 + `data/rival-matrix.json` + `data/rival-depth.json` | 对手自己公开的 sitemap 与页面结构（标题层级、正文词数、表格/列表数），只存指标不存正文 |
| ② 带流量的词清单 | 报告第 2 节；有 GSC 导出时用真数字，没有时照实写"没拿到" | `data/rival-keyword-signals.json`（公开搜索补全的真人查询原话）或 `data/gsc-queries.csv`（操作者从后台导出） |
| ③ 选题队列 | 报告第 8 节 + `data/rival-topic-queue.json` | 三信号排序：我们写没写过 → 补全里排第几（或有流量数据时用后台展示次数）→ 几家对手在做 |

| 这一轮的规矩 | 落点 |
|---|---|
| 不照抄对手原文 | `rival_teardown.py::overlap_check()` 把双方页面切 5-gram 算重合率，对手正文只在内存参与计算、**一字原文都不落盘**。实测：对手 8 页 × 我们 55 个内容页，**内容页最高重合 0.9524%**（6 个 5-gram，出现在 `/about.html`），全站最高 3.7037% 来自只有导航页脚的 `/404.html`。可复跑：`python rival_teardown.py overlap` |
| 不把第三方估算当准数 | 队列排序里没有任何 Ahrefs/Semrush/AITDK 的数字；代码里写成 `::BOUNDARY{never:把 AITDK / sitedata 这类估算当判据|scope:permanent}` |

### 7.2 选题队列接进日更循环（2026-10-03，操作者选的口径：只发"有数据能撑住"的词）

操作者的决定是**先只对"有数据能撑住"的词自动发**，不为了凑词写没有证据的页。落在 `guides.py`：

| 判据 | 实现 | 为什么 |
|---|---|---|
| 哪条词能自动成页 | `queue_builder_for(phrase)` 按词里出现的关键字分三类：`disk`（storage/disk/ssd/nvme/backup）、`ram`（ram/memory）、`price`（cheap/best/price/pricing/cost/budget/affordable） | 这三类正好对应我们抓得到的字段：`disk_gb`、`ram_gb`、`price` |
| 字段够不够 | `build_queue_entry()` 要求该类字段的行数 ≥ `QUEUE_MIN_PLANS = 3`，不够返回 `None` | 只有 1-2 行的"排名"没有信息量，也算不出答案 |
| 数据撑不住的词怎么办 | `queue_entry()` 把它们收进 `skipped` 清单，`main()` 打印 `[note] skipped this run: …`，**原样留在队列里等人工** | 例如 `free vps`、`windows vps uk`、`vps uk`、`unmetered vps`、`server usa`：抓不到"免费/系统/机房位置/不限量"的任何证据，不写 |
| 循环不能断 | 队列里没有可写的词时退回原来的 `csv → unitprice → steps` 轮换（`main()` 里的 `if entry is None` 分支） | 命令要求"每天至少一篇"，队列只是优先项，不是唯一来源 |
| 写出来的页怎么标 | `gap = "queue"`、`queue_phrase = <词>`、`slug = queue-<词>-<日期>-<序号>`，来源在页尾 "What this page is filling" 里写明 | 每个数字都能指回 `data/offers.json`，那一段话里也写明"没有抄任何对手页面" |

**踩到并修掉的口径错误**：第一版把"每 TB 最低价"在**不同货币之间**比，写出
`lowest price per TB is 27.7778 USD/TB`——而我把 EUR 行当成美元直接排序了。这违反站点"按货币分组、不做汇率换算"的
口径（`chart_assets.py` 与 CSV 都是这么做的）。改成：先按行数选主货币组（`_by_currency()` + 行数最多者，并列取字母序），
**最低价只在同一货币内比**，其余货币各自报出自己的领头行。现在这句话是
`in the USD group the lowest price per TB is 27.7778 USD/TB (…) The EUR group (no exchange rate is applied) is led by 67.11 EUR / 1.024 = 65.5371 EUR/TB (netcup VPS 8000 G12.5).`

**第一篇队列页（线上已发）**：`/guide/queue-vps-storage-2026-10-03-1`
（`vps storage`，来自队列第一条；25 档公布了磁盘容量的套餐，USD 组 20 档 + EUR 组 5 档，
两段表格各自按"每 TB 价格"升序）。`content_check.py` 结果 `17/17 篇通过`。
其余 23 条"我们没有写过"的词里，能自动撑住的还有 `best cheap vps` / `best vps`（price 类），
其余留在队列里。

## 8. 事故记录：文章看起来"不更新了"（2026-10-20）

用户的原话是"文章为什么不自动更新了，更新啊"。查下来**日更任务每一天都跑成功了、页面也的确发出去了**，
是另一个每 6 小时跑一次的任务把它们盖回了旧版。

### 8.1 现象

| 看的地方 | 当时的事实 |
| --- | --- |
| 计划任务 `vps-deals-daily` | 09:00 正常触发，`LastTaskResult=1`，NextRun 次日 09:00 |
| `data/daily-log.jsonl` | 从 2026-10-18 起每天 `status: "failed"`，但 `deploy_exit=0`、`verify_exit=0`，只有 `git_exit=1` |
| 失败原文 | `git push: fatal: could not read Username for 'https://github.com': No such file or directory` |
| 2026-10-14 ~ 10-17 | 完全没有日志行（那四天没跑） |
| 本地 | `data/guides.json` 30 篇、`site/guide/*.html` 30 个，本地 `main` 领先 origin 5 个提交 |
| 线上 `/guide` | 只有 24 条链接；最新三篇 `/guide/steps-2026-10-20-1`、`/guide/unitprice-2026-10-19-1`、`/guide/csv-2026-10-18-1` 全部 404 |

也就是说"本机发了、线上没有"，而且线上还变**少**了 6 篇。

### 8.2 根因

1. 本机 `git push` 从 10-18 起失效：`credential.helper=manager` 在无 TTY 的计划任务里弹不出登录窗口，
   `gh auth status` 报 `The token in default is invalid`，也没有 SSH 密钥。于是 origin/main 停在 10-17 的版本。
2. `.github/workflows/update.yml` 的 cron 是 `17 */6 * * *`，它 checkout 的是 **origin/main（旧）**，
   抓数据、构建、提交 `data: refresh …`，然后 `wrangler pages deploy site --branch=main`。
   `main` 当时就是生产分支，于是每 6 小时用旧内容覆盖一次 production。
   `wrangler pages deployment list` 里 12:45 那次 Production 部署的 source commit `68c6aec`
   在本地根本不存在——那是 Actions 自己造的刷新提交，本地不知道。
3. 还有一个放大问题：deploy 步骤的条件写成 `if: ${{ env.CLOUDFLARE_API_TOKEN != '' }}`，
   这覆盖了隐式的 `success()`，于是前面 push 失败它也照发——发布了一份没进仓库的构建。

### 8.3 修法

| 改动 | 位置 | 为什么这样做 |
| --- | --- | --- |
| 生产分支从 `main` 改成 `production` | Cloudflare Pages 项目设置（API `PATCH /accounts/<id>/pages/projects/vps-deals-promo-radar`，`{"production_branch":"production"}` → 200） | 让 Actions 在 `main` 上的部署落到**预览地址**，production 只由本机日更发。域名 `vpsdealsradar.com` 不变 |
| 部署带 `--branch=production` | `daily.py::deploy()`（可用 `PAGES_BRANCH` 覆盖） | 本机发的就是生产 |
| deploy 条件加 `success()`，改名 preview | `.github/workflows/update.yml` | 前面失败就不发布；preview 只当"干净环境也能构建"的冒烟测试 |
| `site/` 移出版本库 | `.gitignore` + `git rm -r --cached site` + `daily.py` 只 `git add data` | 生成物不该被两边各提交一次，那是冲突与覆盖的来源 |
| 抓取失败不拖停发布 | `scraper.py::fetch_retry()` + `main()` 的沿用上次结果 | 见 8.5 |

修完立刻恢复：`python daily.py`（`2026-10-20T05:45:56Z`）全绿，
`offers 30 / priced 30 / guides 30 / guard_exit 0 / deploy_exit 0 / verify_exit 0`，
只有 `git_exit 1`（凭据待处理）。线上复核：`线上 404 的指南页: 0`，`/guide` 重新是 30 篇。
首页与本地 diff 只差 Cloudflare 自动注入的 `beacon.min.js` 一行——之前以为"线上是旧版"，一半是这条脚本的噪声。

### 8.4 还没解决的

- **push 凭据**：需要一次 `gh auth login -h github.com`（或者给一个 PAT）。在此之前本机提交只累积在本地。
  站点内容不受影响，但 `data/daily-log.jsonl` 会一直记 `status: "failed"`——这是**诚实的失败**，不是站点坏了。

### 8.5 顺带修的第二件事：一次抓取失败不该让当天没页

修的过程中复现了一次：netcup 那一页抓取超时 → `guard.py` 报
`[fail] scrape regressed, provider(s) lost every offer: netcup (10 -> 0)` → 当天不发页。
netcup 页面本身是好的，重试就恢复，但这说明"一次网络抖动 = 断更一天"。

- `fetch_retry(url, attempts=3)`：只对"没拿到内容"（连接错误 / 5xx / 空响应）重试，`4xx` 立即返回，
  不反复打扰对方站点，间隔 4 秒。
- 彻底失败时**沿用上一次成功读到的数据**，每档标 `stale`，`fetched_at` 保持原值，
  并在厂商页写明：`Every attempt to re-read this page failed (<错误>). The N plan(s) below are the ones read at <时间>: kept and marked stale rather than dropped, and nothing here is estimated.`
- 有意的边界：`guard.py` 只比"某家从有到无"，兜底后计数不变就放行；**真·整批下架**（页面读到了但抽不出任何套餐）
  仍然会被拦。兜底不等于放水——旧数据标了 stale，没有变成估算。
- 验证（monkeypatch 让 netcup 必失败）：`总档数: 30 / netcup 档数: 10 | stale 标记: 10`，
  `netcup 保留的 fetched_at: ['2026-10-20T04:45:15Z']`，脚本用完即删。
